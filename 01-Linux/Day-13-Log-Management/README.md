## 📖 Theory Explained

### What Are Logs?

**Logs** are chronological records of events generated by:

- **Linux**
- **Applications**
- **Services**
- **Databases**
- **Web servers**

Example:

```
2026-08-07 14:21:53 INFO Server started on port 3000
```

### Common Log Locations

Most Linux logs are stored under:

```
/var/log/
```

Examples:

| File | Purpose |
|------|---------|
| `/var/log/syslog` | General system activity |
| `/var/log/auth.log` | Authentication and login events |
| `/var/log/kern.log` | Kernel messages |

> ⚠️ Depending on your distribution, some filenames differ (e.g. Debian/Ubuntu use `auth.log`, while some use `secure`).

### Application Logs

Examples:

| File | Purpose |
|------|---------|
| `/var/log/nginx/access.log` | Nginx web server requests |
| `/var/log/nginx/error.log` | Nginx errors |
| `/var/log/mongodb/mongod.log` | MongoDB database activity |

Node.js applications often write logs to:

```
logs/app.log
```

...or to **stdout**, where systemd captures them (viewable with `journalctl`).

### Viewing Logs

| Task | Command | Notes |
|------|---------|-------|
| Entire file | `cat app.log` | ⚠️ Avoid this for large logs |
| First lines | `head app.log` | |
| Last lines | `tail app.log` | |
| Follow live logs | `tail -f app.log` | Watch new entries as they arrive |
| Browse large logs | `less app.log` | Scrollable with search |

Useful `less` navigation:

| Key | Action |
|-----|--------|
| `/error` | Search for text |
| `n` | Next result |
| `q` | Quit |

### Searching Logs

Find all errors:

```bash
grep ERROR app.log
```

Case-insensitive:

```bash
grep -i error app.log
```

Count matches:

```bash
grep -c ERROR app.log
```

Show line numbers:

```bash
grep -n ERROR app.log
```

### Viewing Service Logs

For services managed by **systemd**:

```bash
journalctl -u myapp
```

Latest 20 entries:

```bash
journalctl -u myapp -n 20
```

Live view:

```bash
journalctl -u myapp -f
```

### Understanding Log Levels

| Level | Meaning |
|-------|---------|
| `DEBUG` | Detailed diagnostic information |
| `INFO` | Normal operation |
| `WARN` | Something unexpected but not fatal |
| `ERROR` | An operation failed |
| `FATAL` | Critical failure; the application may stop |

### Log Rotation

Without maintenance, logs grow indefinitely.

Linux commonly uses **`logrotate`**, which provides:

- **Compresses** old logs.
- **Creates** new log files.
- **Deletes** very old logs.
- **Prevents** disks from filling up.

Typical rotation:

```
app.log  →  app.log.1  →  app.log.2.gz
```

As the current log fills, the previous one is renamed, and older ones are compressed before eventually being removed.

## 🌍 Real-World MERN Example

### Production Incident

Users receive:

```
500 Internal Server Error
```

### Step 1 — Check service status

```bash
sudo systemctl status myapp
```

### Step 2 — View recent service logs

```bash
journalctl -u myapp -n 50
```

Output:

```
MongoNetworkError: failed to connect
```

### Step 3 — Inspect MongoDB logs

```bash
tail -50 /var/log/mongodb/mongod.log
```

### Step 4 — Find connection errors

```bash
grep -i "connection" /var/log/mongodb/mongod.log
```

### Root cause

**MongoDB service wasn't running.**

By following the logs, I identified that the backend errors came from a failed MongoDB connection — not from the application code itself. Restarting MongoDB fixed the issue.

## ✅ Best Practices

1. **Check logs before restarting services** — Capture the evidence before taking action.
2. **Log meaningful events, not excessive noise** — Too much noise hides real problems.
3. **Rotate logs regularly** — Prevents disks from filling up.
4. **Separate access logs from error logs** — Easier to analyze and secure.
5. **Monitor logs for recurring patterns** — Rather than isolated events.
6. **Protect logs that may contain sensitive information** — Restrict permissions and encrypt where needed.

---

## ❌ Common Mistakes

1. **Ignoring warnings until they become errors** — Warnings are early signals.
2. **Using `cat` on multi-gigabyte log files** — Slows the system and floods the terminal.
3. **Not rotating logs, leading to full disks** — Disk-full causes outages.
4. **Logging passwords, API keys, or other secrets** — A serious security risk.
5. **Restarting applications before capturing useful log evidence** — Destroys the ability to diagnose.

## 💼 Interview Questions

### Beginner

**Q1: Why are logs important?**
> Logs provide a chronological record of events that helps diagnose problems, understand system behavior, audit security, and troubleshoot production issues without guessing.

**Q2: Where are Linux system logs commonly stored?**
> Under `/var/log/` — for example `/var/log/syslog`, `/var/log/auth.log`, and `/var/log/kern.log`.

**Q3: What does `tail -f` do?**
> It displays the last lines of a file and **follows** the file, showing new entries in real time as they are appended.

**Q4: What is the purpose of `grep`?**
> `grep` searches files for matching text patterns, letting me filter log files to find relevant lines quickly.

**Q5: What is `journalctl`?**
> `journalctl` is the tool used to query logs collected by **systemd's journal**, including logs for systemd-managed services (e.g., `journalctl -u myapp`).

### Intermediate

**Q6: Explain different log levels.**
> Log levels indicate severity: **DEBUG** (detailed diagnostics), **INFO** (normal operation), **WARN** (unexpected but not fatal), **ERROR** (an operation failed), **FATAL** (critical failure — the application may stop). Filtering by level helps focus on the most important entries.

**Q7: Why is log rotation necessary?**
> Without rotation, logs grow indefinitely and fill up the disk, causing outages. Rotation compresses old logs, creates new ones, and deletes very old ones to keep disk usage manageable.

**Q8: How would you investigate repeated login failures?**
> Check `/var/log/auth.log` for authentication attempts, search for `failed` or `invalid` entries, look for patterns (e.g., same IP, brute force), and correlate with application logs to determine the cause.

**Q9: How do you search for errors in a log file?**
> Use `grep ERROR app.log`, or case-insensitive `grep -i error app.log`. For line numbers, add `-n`. For a live service, use `journalctl -u service -n 50`.

**Q10: What are the advantages of structured logging?**
> Structured logging (e.g., JSON) makes logs machine-readable, easier to parse, filter, and aggregate in centralized logging platforms, and enables richer querying and correlation.

### Advanced

**Q11: Design a logging strategy for a production MERN application.**
> A robust strategy includes: separate Nginx access/error logs, structured application logs (request IDs, timestamps, user context), MongoDB logs, centralized aggregation (e.g., ELK), log level filtering, rotation policy, retention based on compliance, and alerting on ERROR/FATAL patterns.

**Q12: How would you investigate intermittent API failures?**
> Correlate application logs with Nginx access/error logs and server metrics. Look for timeouts, resource exhaustion, slow queries, and patterns tied to specific times or endpoints. Use `journalctl` and `tail -f` during reproduction, and add request IDs to trace the full path.

**Q13: What are the risks of logging sensitive information?**
> Logs may be accessible to others and retained for long periods. Logging passwords, API keys, or personal data creates a security and compliance risk. Secrets should be masked or excluded entirely.

**Q14: How do centralized logging platforms improve operations?**
> They aggregate logs from many servers into one place, enable fast search and correlation, provide dashboards and alerts, support retention, and help identify system-wide issues rather than isolated events.

**Q15: Describe a log-based incident response workflow.**
> 1) Detect the incident (alert or user report). 2) Capture and preserve logs before acting. 3) Identify the relevant log source (app, Nginx, DB, system). 4) Search/filter for errors around the incident time. 5) Determine the root cause. 6) Apply a fix. 7) Verify in logs that the issue is resolved. 8) Document and add monitoring/alerts to prevent recurrence.

## 👨‍💻 Coding Exercise

### log_summary.sh

Create `log_summary.sh`:

```bash
#!/bin/bash

LOGFILE="app.log"

echo "===== Total Lines ====="
wc -l "$LOGFILE"

echo
echo "===== Errors ====="
grep -c "ERROR" "$LOGFILE"

echo
echo "===== Warnings ====="
grep -c "WARN" "$LOGFILE"

echo
echo "===== Last Five Entries ====="
tail -5 "$LOGFILE"
```

**Make it executable:**
```bash
chmod +x log_summary.sh
```

**Run it:**
```bash
./log_summary.sh
```

**What I learned:**
- `wc -l` — Counts the total number of lines
- `grep -c` — Counts matching lines
- `tail -5` — Shows the last 5 lines

### Lab: Investigate a Failed MERN Deployment

Create a sample log file containing:

- `INFO` entries
- `WARN` entries
- `ERROR` entries

**Tasks:**

1. Count `ERROR` messages.
2. Display only `WARN` messages.
3. Show the last 10 lines.
4. Follow the log live.
5. Write a short incident summary identifying the probable root cause.

**Example log file (`deploy.log`):**
```bash
cat > deploy.log <<EOF
INFO Starting deployment
INFO Stopping old containers
ERROR Failed to pull image: connection refused
WARN Retrying image pull
INFO Pulled image successfully
INFO Starting new containers
ERROR Container health check failed on worker-1
WARN Restarting worker-1
INFO Worker-1 healthy after restart
INFO Deployment complete
EOF
```

**Commands to complete the tasks:**
```bash
# 1. Count ERROR messages
grep -c "ERROR" deploy.log

# 2. Display only WARN messages
grep "WARN" deploy.log

# 3. Show the last 10 lines
tail -10 deploy.log

# 4. Follow the log live
tail -f deploy.log
```

**5. Incident summary:** The deployment initially failed to pull the image due to a connection error, then a worker's health check failed on startup. After a restart, the worker recovered and the deployment completed. The probable root cause was a transient network/registry connectivity issue during the pull phase.

Include the following log sources:
